# Lesson 260 — G8.19.T4 auditoria de workflows N8N críticos (2026-07-18)

## Contexto

O repositório tinha 40 exports JSON de workflows na raiz, mas não havia uma trilha local que unisse identidade do workflow, hash estrutural e autoria das mudanças Git. Consultar o n8n live não era permitido nesta task.

## Decisão

Foi criado `scripts/n8n_wf_audit.py`, uma CLI stdlib-only e offline. O relatório relaciona cada workflow catalogado com:

- ID do n8n ou fallback `local:<nome>` para templates;
- SHA256 do JSON estrutural canônico;
- threshold `critical` ou `high`;
- commit, autor, email, timestamp UTC e assunto.

O comando `git log --follow` precisa de exatamente um path. Por isso o auditor consulta cada workflow separadamente, em vez de repetir o esqueleto inválido que combinava `--follow` com vários pathspecs.

## Otimização

`_git_log_cached` usa `functools.lru_cache` com `(repo, workflow, HEAD)`. Chamadas repetidas no mesmo processo não abrem outro subprocesso; um novo commit altera `HEAD` e invalida a chave de forma determinística.

## LGPD

O hash exclui campos de execução ou metadados voláteis (`pinData`, `staticData`, timestamps e version IDs). A entrada é somente a definição local do workflow, nunca payload de execução. O relatório expõe o digest, não o conteúdo dos nodes. O lint anti-PII dos exports continua sendo um gate independente e obrigatório.

## Dead-man's-switch

A integração deve consumir `--critical-only --since <ultimo_check>`, alertar quando houver modificações e exigir HITL antes de aceitar um hash novo. O auditor não ativa workflows e não escreve na cadeia de auditoria; o serviço owner preserva append-only e HMAC.
